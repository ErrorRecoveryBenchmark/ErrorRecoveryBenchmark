# Training Recovery Demo Pipeline Overview

This document provides a quick overview of the pipeline. The term `training source demo` refers to the data source used for recovery training, i.e., the `training recovery demo`.

The entire pipeline can be understood as two steps:

- Step one: humans collect a small batch of high-quality `RecoveryDemo` from error scenes; these are the source demos.
- Step two: use MimicGen/IntervenGen-style methods to augment these source demos into more `AugmentedRecovery` trajectories.

Finally, Stage 4 converts both parts together into MCM/diffusion training data.

## 1. Full Pipeline Overview

```text
v5 error scenes
error_benchmark/outputs/v5_training/{task}/scenes/*.json + *.npz
        |
        |  Stage 1: human collection
        v
error_benchmark/scripts/collection/2_collect_recovery_demos.py
        |
        v
error_benchmark/outputs/recovery/demos/{task}/{subtype_id}/recovery_*.npz
        |
        |  These are the source demos / RecoveryDemo
        |
        |  Stage 3: MimicGen-style augmentation
        v
error_benchmark/scripts/augmentation/3_mimicgen_recovery_augment.py
        |
        v
error_benchmark/outputs/recovery/augmented/{task}/{subtype_id}/aug_*.npz
        |
        |  Stage 4: training conversion
        v
4a_generate_mcm_training_data.py
4b_generate_diffusion_training_data.py
```

## 2. Key Concepts in This Pipeline

### 2.1 Error Scene

Sourced from the v5 error injection pipeline:

- `error_benchmark/outputs/v5_training/{task}/scenes/*.json`
- `error_benchmark/outputs/v5_training/{task}/scenes/*.npz`

Each scene represents an initial state with an injected error; all subsequent recovery demos start from here.

### 2.2 RecoveryDemo

This is the recovery demonstration collected via human teleoperation, and the most important source demo in this pipeline.

It essentially answers:

- After encountering a specific error, how should the robot arm recover step by step and continue completing the task.

### 2.3 AugmentedRecovery

These are augmented recovery trajectories generated from existing `RecoveryDemo` data.

Its purpose is:

- No longer completely relying on manual collection one by one
- Expanding a small number of recovery demos into a larger training set

## 3. Stage 1: Human Collection of Source Recovery Demos

Entry script:

- `error_benchmark/scripts/collection/2_collect_recovery_demos.py`

### 3.1 What Are the Inputs

It consumes the error scenes generated by v5:

- `outputs/v5_training/{task}/scenes/{scene_id}.json`
- `outputs/v5_training/{task}/scenes/{scene_id}.npz`

The script restores the environment to `post_sim_state`, i.e., the state after the error has occurred.

### 3.2 What It Does Specifically

The workflow of this stage can be summarized as:

1. Load error scene
2. Replay injection process so the operator understands how the error occurred
3. Perform teleoperated recovery using SpaceMouse/Keyboard
4. Record the complete recovery trajectory
5. Automatically perform subtask segmentation
6. Perform post-collection validation to determine if this demo is suitable for augmentation

These correspond to the following in code:

- Collection entry: `2_collect_recovery_demos.py`
- Segmenter: `error_benchmark/framework/recovery_segmenter.py`
- Post-collection validation: `error_benchmark/framework/recovery_collection_validation.py`

### 3.3 Where Outputs Are Stored

Main directory:

- `error_benchmark/outputs/recovery/demos/{task}/`

Key files:

- `manifest.json`
- `human_demo_test_report.json`
- `{subtype_id}/recovery_{task}_{subtype_id}_xxxx.npz`

The `recovery_*.npz` files here are the source demo data itself, serving as input for subsequent recovery augmentation.

## 4. Stage 1b: Backfill Source Demos to Augmentation-Ready Version

Entry script:

- `error_benchmark/scripts/augmentation/backfill_recovery_target_poses.py`

The background for this step is:

- Early collected demos may have only recorded `actions` and `eef_positions`
- But the Stage 3 augmenter requires source demos to also have `target_poses`, `eef_orientations`, and valid `subtasks`

So this step does not add new data, but fills in fields needed for augmentation in existing `RecoveryDemo`.

If a demo is missing these fields, `RecoveryAugmenter._validate_source_demo()` will raise an error directly.

## 5. Stage 3: Augment Recovery Demos Using MimicGen-Style Methods

Entry script:

- `error_benchmark/scripts/augmentation/3_mimicgen_recovery_augment.py`

### 5.1 Inputs for This Step

There are two types of inputs:

- source demos: human `RecoveryDemo` under `outputs/recovery/demos/{task}/...`
- target scenes: error scenes under `outputs/v5_training/{task}/scenes/...`

Think of it as:

- We first have a source trajectory showing "how the human recovered"
- Then we transfer this recovery trajectory to other error scenes to see if it still succeeds

### 5.2 What the Augmenter Actually Does

The core is `augment_scene()`:

- First load source `RecoveryDemo`
- Then load target error scenes
- Segment recovery trajectory by subtask
- Perform object-centric warping / target pose replay
- Execute in simulation and verify
- Only successful ones are saved as `AugmentedRecovery`

Besides the main path `3A scene augmentation`, the script also includes two extensions:

- `3B cross-degree`：D0 → D1
- `3C cross-subtype`: transfer across subtypes within the same RBG

For understanding purposes, just remember it as "taking existing recovery demos and performing MimicGen-style augmentation in new scenes".

### 5.3 Where Outputs Are Stored

Main directory:

- `error_benchmark/outputs/recovery/augmented/{task}/`

Key files:

- `augmentation_manifest.json`
- `{subtype_id}/aug_*.npz`

These `aug_*.npz` files are the recovery training demos generated by the second pipeline path.

## 6. Stage 4: Convert Human Demos and Augmented Demos Together into Training Data

This is where the two pipeline paths truly merge.

### 6.1 MCM Data

Entry:

- `error_benchmark/scripts/conversion/4a_generate_mcm_training_data.py`

By default reads:

- `outputs/recovery/demos/{task}/manifest.json`

That is, it defaults to using human `RecoveryDemo` first.

If you add:

- `--include_augmented`

It will also read:

- `outputs/recovery/augmented/{task}/augmentation_manifest.json`

Including `AugmentedRecovery` as well.

### 6.2 Diffusion Data

Entry:

- `error_benchmark/scripts/conversion/4b_generate_diffusion_training_data.py`

Logic is the same as MCM:

- Defaults to consuming human `RecoveryDemo`
- With `--include_augmented`, includes `AugmentedRecovery` in the training set

So Stage 4 can be understood as:

- human source demos are the base set
- augmented demos are the extension set
- Together they form the final training set

## 7. What Role Does `prepared_source/{task}_src.hdf5` Play in This Pipeline

This file is easily mistaken for a "source demo", but in the recovery mainline it is not the source recovery demo itself.

It is more like a foundational dependency for the MimicGen side:

- `RecoveryAugmenter._get_env_interface()` reads `env_interface` from here
- The `scene aug preflight` in post-collection validation also depends on it

So a more accurate understanding is:

- `RecoveryDemo` is the actual source demo in our pipeline
- `prepared_source/{task}_src.hdf5` is a base dataset prepared to make the MimicGen-style augmenter work correctly

## 9. How to Introduce This Pipeline

In a few sentences:

1. We first collect a small batch of recovery demos via human teleoperation from v5-generated error scenes; these are the source demos.
2. Then we use MimicGen-style trajectory transfer and scene resampling to augment these source demos into more recovery trajectories.
3. Finally in Stage 4, we convert human demos and augmented demos together into MCM/diffusion training data.

## 10. Shortest Summary

One-sentence summary:

- The core of this pipeline is: "first manually collect source recovery demos, then augment them into augmented recovery demos using MimicGen-style methods, and finally convert both together for training".
